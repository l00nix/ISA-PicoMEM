# USB transport failure detail

I added a firmware-only diagnostic to distinguish the two possible meanings of
`c6=phase` in the [PPC512 cache-mode result](USB-CACHE-MODE.md): a phase-error CSW
returned by the device, or a synthetic status generated by the checked TinyUSB
transport. **The PPC512 test captured a MODE SENSE(6) DATA/residue mismatch. Reads pass; Kingston write-cache state remains unknown and writes remain blocked.**

## What changes

Before replacing an invalid completion with a synthetic CSW, TinyUSB records the
command tag/opcode, transfer stage/event, actual and expected endpoint/byte count,
DATA byte count, and available CSW checks/status/residue. A genuine device phase
error is recorded separately. The acceptance checks and command sequence are
unchanged. There are no additional USB commands, endpoint clears, resets, retries,
MODE SELECT commands or synchronization bypasses.

The driver keeps the first failure for a command. The getter requires the matching
tag and a valid device address; a new command or device close clears that driver
snapshot. On a validated cache-query status-2 callback, the adapter immediately
copies it into permanent bounded text. Late callbacks and detach cannot replace
that text. Submission failure, timeout or detach without a transfer callback can
still lack this detail; absence of detail is not success.

`pmstat --usb` retains the original flush/sense/cache line and appends three cached
lines. For illustration only, a DATA-stage stall would look like this; this is
**a host-test example, not a PPC512 result**:

```text
USB fault op=1a tag=3 why=1 stage=2 event=2
USB xfer ep=81/81 got=0 want=64 data=0
USB CSW checks=00 status=255 residue=4294967295
```

Each line is at most 79 bytes plus its terminator. The appender checks the original
count and terminators and appends all three or none within the existing 1024-byte,
eight-line response. With at most four USB devices the total is at most eight
lines. Reading this report submits no USB commands. No ELKS kernel or utility
update is required.

## Field meanings

| Field | Meaning |
| --- | --- |
| `op`, `tag` | Opcode in hexadecimal and decimal command tag for the failed cache query. The original flush fault remains in its own line. |
| `why` | 1: transfer event; 2: wrong endpoint; 3: invalid length; 4: CSW signature; 5: CSW tag; 6: residue out of range; 7: invalid status; 8: DATA/residue mismatch; 9: valid device phase-error CSW. Checks are classified in this order, except a valid status 2 is reason 9. |
| `stage` | 1: command/CBW; 2: DATA; 3: status/CSW. |
| `event` | Pinned TinyUSB event: 0 success, 1 failed, 2 stalled, 3 timeout, 4 invalid. An unsuccessful event's byte count is recorded raw; it does not make payload bytes trustworthy. |
| `ep` | Actual/expected endpoint in hexadecimal. |
| `got`, `want` | Actual event bytes/requested stage bytes. A diagnostic DATA response may legitimately be shorter than the allocation. |
| `data` | DATA event count for a DATA-stage fault; otherwise the last accepted DATA-stage byte count. |
| `checks` | Hex bitmask: 01 complete available CSW, 02 correct signature, 04 matching tag, 08 residue in range, 10 status in range, 20 DATA/residue agreement. These are observations; a failed overall check is still quarantined. |
| `status`, `residue` | Raw device fields only when a successful, correctly addressed, exactly 13-byte CSW was received. Otherwise sentinel 255 / 4294967295 means unavailable, not a device response. |

The record is captured before synthetic-CSW replacement. No partial, failed or
wrong-endpoint status transfer is interpreted as a device CSW. Reason 9 requires
the existing valid CSW checks; it does not imply a usable cache page.

## Validation

- 18,430 actual patched-TinyUSB completion/length/status cases with ASan/UBSan,
  including raw-versus-synthetic provenance, all failure classes, bounded getter,
  snapshot reset, stale CSW exclusion and late-event preservation.
- 151 actual adapter scenarios with ASan/UBSan, including all response capacities
  from 0 through 1024, counts 0 through 8, malformed input, maximum field values,
  immutable cached lines, and no extra USB submissions from status formatting.
- Five actual FatFs/mount scenarios using disposable FAT32 images and independent
  long-name/content readback; 14 legacy USB tests.
- 29 existing ELKS status-parser scenarios, including the extended eight-line
  response. This tests the existing client code without changing its binary.
- ARM build and linker stack-layout check pass: 4096-byte core-0 reservation,
  2048-byte core-1 reservation, no scratch overlap. Runtime fault-path peak still
  needs measurement. RAM rises by 352 bytes and flash by 1392 bytes from the
  cache-mode build.
- The feature-disabled UF2 is byte-identical to its previous artifact. Both the
  patched MSC C source and header hashes are checked at CMake configuration;
  `tools/prepare-lfn-deps.py` verifies the exact pinned dependency patch.

## PPC512 transport-detail result

The full recovery backup and firmware readback passed. ELKS booted with the
existing kernel, USB appeared immediately, and all eight retained files passed
full-content verification through a read-only mount. After unmounting and mounting
explicitly read/write, one fresh `mkdir /mnt/usb/PMTRN29` failed with exit 1.
The cached result was:

```text
?USB fault op=35 f=2 s=1 r=0 d=0 rs=70:5/20/00 n=18 c6=phase c10=-
USB fault op=1a tag=427 why=8 stage=3 event=0
USB xfer ep=81/81 got=13 want=13 data=4
USB CSW checks=1f status=0 residue=0
```

The first cache query failed the **DATA/residue agreement check**. TinyUSB recorded
four DATA bytes for the 64-byte allocation, followed by a successful 13-byte CSW
transfer on the expected endpoint. The raw CSW had a valid signature, matching
tag, bounded residue and status 0, but residue 0 claims all 64 requested bytes
were relevant. The agreement bit `20` is missing from `checks=1f`. The checked
transport then generated synthetic status 2; the device CSW itself did not report
a phase error. MODE SENSE(10) was correctly skipped under the existing policy.

For Data-In, the [USB Bulk-Only Transport specification, section 5.2](https://www.usb.org/sites/default/files/usbmassbulk_10.pdf)
defines residue from the requested length and relevant bytes returned. The observed
counts therefore do not establish a trustworthy cache-page response. This is
firmware-observed evidence, not a physical bus trace: a device reporting an
incorrect residue is one possibility, but a host byte-count problem is not ruled
out. The four raw mode bytes were not captured, so I cannot yet call this an empty
mode header or infer the write-cache setting. **Cache state remains unknown.**

[Hardware screenshot and ELKS evidence](https://github.com/l00nix/picomem-elks/blob/codex/usb-sync-lifetime/docs/USB-SYNC-LIFETIME.md#transport-detail-ppc512-result).

The screenshot comes from actual PPC B800 video memory with live mount/status
output and the explicitly saved native mkdir error. I did not repeat the write.
The pre-write guard returned before sector-write submission, inferred from the
control flow and original `dirty=0` fault rather than a USB trace. USB unmounted
successfully; SD stayed unmounted. Initial stack use was 1632/4096 firmware bytes
and 418/700 kernel bytes with zero flags/invalid counts. Fault-path peak use was
not measured. ELKS remains running with the fault latched until PicoMEM restarts.

My next proposed diagnostic is a bounded capture of returned mode bytes and
MODE SENSE(10) as the **first** cache query on a fresh boot. That would test the
alternate command without continuing after this ambiguous MODE SENSE(6) response.
It is not implemented or flashed yet. Strict transport checks, write quarantine
and the flush requirement remain; no cache-setting change or write retry was made.

The [MODE SENSE(10)-first / raw-prefix follow-up](USB-MODE10-PREFIX.md) is now built and host-tested; hardware validation is pending.
